#### 1.6.2 React Aria warnings, aria base

React Aria's `Focusable` and `Pressable` check their child in order: it must be focusable (else "must be focusable"), then, unless it is a native control, it needs an interactive role (else "interactive ARIA role"). `useLabel` warns on a field without a visible label, `aria-label` or `aria-labelledby`. The library stops producing the four messages at the source; the parts under `components/ui/` are not edited.

- Does: the five anchor spans no longer sit inside a `Pressable` that warns; the span stays `aria-hidden`, out of the Tab order and non-interactive for assistive technology (D26); the opener keeps `aria-haspopup` and `aria-expanded`; the `MenuOpeners` play test (Tab never lands on the span, second click closes) stays green
- Does: `ST_Tooltip` (aria) renders its `TooltipTrigger` only around a child that can take focus; for a child that cannot (a disabled page button, a control inside the inert search panel, a non-focusable span or label) it renders the child alone; `onOpenChange` is wired so Escape and blur close a tooltip opened by the library's `open` state (React Aria's design)
- Does: `ST_ExpandButton`, `ST_ExpandAllButton`: the `Button` is the tooltip child, no span; `ST_SelectCheckbox`, `ST_FilterCheckbox`, `getST_RowExpandColumnDef`: the tooltip text becomes the control's accessible name (`aria-label` on the `Checkbox` or `RadioGroup`, `title` on the grouping value span) and the `ST_Tooltip` wrapper goes where its child is not focusable; the texts stay the localization strings they are today
- Does: `ST_TablePagination` `Select` gets `aria-label={localization.rowsPerPage}` on the `Select` (kept on the trigger too); `ST_LinearProgressBar` `Progress` gets `aria-label` from the loading localization string; `ST_FilterRangeSlider` `Slider` gets `aria-label` from the column header text (the filter label the text field variant already uses)
- Does NOT change base or radix for this component, the menu anchor hook, any part file, or any exported prop; a tooltip removed for accessibility reasons is replaced by the control's accessible name, never dropped silently

**Stays unchanged:** `input-group.tsx` part, `ST_ToggleGlobalFilterButton`.

#### 1.6.4 Escape from the full-screen toggle, all bases

React Aria's `useTooltipTrigger` registers a capture-phase `keydown` listener on `document` while a tooltip is open and stops Escape there, so no element handler sees it; the toggle's tooltip reopens after a click because entering full screen moves the button under the pointer. The container handles Escape before any part can.

- Does: `useST_FullScreenContainer` adds `'data-st-full-screen': ''` to `containerProps` (widening, D29) and, while `isFullScreen`, a capture-phase `keydown` listener on `document` that calls `table.setIsFullScreen(false)` when the key is `Escape`, the target lies inside the element carrying `data-st-full-screen`, and the target is not an `input`, `textarea`, `select` or `[contenteditable]` element; portaled menus, popovers and dialogs lie outside the container and are untouched; the element `onKeyDown` stays as the fallback and for the headless API
- Does: aria `ST_Tooltip` `onOpenChange` (1.6.2) so the tooltip also closes on that Escape
- Does NOT change `ST_TableLayout`, the headless example, or the `ST_FullScreenContainer` type beyond the new attribute key in `containerProps`

**Interfaces:**

```typescript
export interface ST_FullScreenContainer {
  readonly isFullScreen: boolean;
  readonly containerProps: {
    readonly className: string;
    readonly onKeyDown: (event: React.KeyboardEvent<HTMLElement>) => void;
    readonly tabIndex: number | undefined;
    readonly 'data-st-full-screen': '';
  };
}
```

**Stays unchanged:** `ST_ToggleFullScreenButton` behavior (tooltip on focus and hover, closed on click), the full-screen classes.
